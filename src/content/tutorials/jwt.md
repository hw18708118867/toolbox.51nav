## 一次"验签永远通过"的联调事故

前阵子联调一个登录接口，后端同学说"你这个 JWT 验不过"。我把 token 贴进库里的验证脚本，居然每次都返回 true。排查半天才发现，那脚本是用公钥验证的，而我手贱把 alg 改成了 HS256，后端的验证代码看到 HS256 就拿公钥当 HMAC 密钥去算——公钥是公开的，等于没设防。

这就是 JWT 最经典的坑：算法混淆攻击。本文把 JWT 的结构、两种主流签名算法、还有时间声明一次讲清，并告诉你怎么用本工具安全地签发和验签。

## JWT 就是三段 base64url，中间用点隔开

一个典型的 JWT 长这样：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

三段分别是：

| 段 | 名称 | 内容 | 是否可篡改 |
|----|------|------|-----------|
| 第 1 段 | Header | 算法、令牌类型，如 `{"alg":"HS256","typ":"JWT"}` | 能改，但改了签名就对不上 |
| 第 2 段 | Payload | 业务声明（claims），如用户 ID、过期时间 | 能改，同样签名会对不上 |
| 第 3 段 | Signature | 对前两段的签名值 | 由密钥/私钥算出，别人算不出 |

关键认知：**Payload 只是 base64url 编码，不是加密**。任何人都能解码看到里面的内容。所以别往 JWT 里塞密码、身份证号这种敏感信息。

## HS256 和 RS256：对称还是非对称

| 对比 | HS256（HMAC） | RS256（RSA） |
|------|--------------|--------------|
| 密钥 | 一个共享密钥（secret） | 一对：私钥签名、公钥验证 |
| 签名方 | 服务端持有密钥 | 用私钥签名 |
| 验证方 | 也用同一个密钥 | 用公开的公钥验证 |
| 适用 | 自己签发自己验证的单体服务 | 多服务/第三方需要验证的场景 |
| 风险点 | 密钥泄露=可随意伪造 | 私钥泄露才危险，公钥本就可公开 |

RS256 的好处是：签发服务的私钥可以严格保管，而验证方只需要拿到公钥，公钥泄露不会让任何人伪造 token。这正是对抗上面"算法混淆攻击"的基础——验证端必须固定死只允许 RS256，并只用公钥验。

## 三个时间声明：iat / nbf / exp

Payload 里经常看到这组时间戳，单位是**秒**（不是毫秒），从 1970-01-01 算：

- `iat`（issued at）：签发时间。用来判断 token 是不是"未来才签发"的。
- `nbf`（not before）：生效时间。在此之前 token 不可用，常用于"预约生效"。
- `exp`（expiration）：过期时间。最常见的，登录态失效就靠它。

本工具解码后会自动把这三个字段转成可读时间，并标出状态：已过期 / 还剩多久 / 尚未生效。注意**比对时务必用秒级时间戳**，很多人拿毫秒往 `exp` 里塞，结果 token 在 1970 年附近就"过期"了。

## 用本工具签发一段 JWT

打开 JWT 工具的"生成 / 签名"标签：

1. 选算法：联调自家用 HS256，对接外部用 RS256/RS384/RS512。
2. 编辑 Header（默认带 `alg` 和 `typ`，改算法会自动同步）。
3. 编辑 Payload，可用"插入 iat / exp(+1h) / nbf"按钮快速加时间声明。
4. HS 系列填密钥，RS 系列贴 RSA 私钥（PEM，`BEGIN PRIVATE KEY` 或 `BEGIN RSA PRIVATE KEY` 都支持）。
5. 点"生成 Token"，得到三段式字符串，一键复制。

整个过程在浏览器本地完成，密钥和私钥不会上传到任何服务器——这也是这类敏感操作不该用网页后端代理的原因。

## 验证签名：对得上才是真的

切到"解析 / 验证"标签，粘贴 token：

- 工具立刻解码出 Header 和 Payload，并列出时间声明的状态。
- 根据 Header 里的 `alg`：HS 系列填密钥点"验证签名"；RS 系列贴公钥（PEM）点验证。
- 结果显示"签名有效 ✓"或"签名无效 ✗"，无效通常意味着内容被改过或你给的密钥/公钥不对。

记住前面的坑：验证端要固定算法。如果别人给你一个 RS256 的 token，你却用 HS256 + 公钥去验，公钥是明文，等于拿公开字符串当 HMAC 密钥——这正是被攻击的姿势。正规实现应拒绝任何非预期算法。

## 常见问题

**Q：JWT 能当加密用吗？**
不能。Payload 只是编码，谁都能解码看。要保密得用 JWE 或在传输层用 HTTPS，敏感字段别放进去。

**Q：HS256 的密钥要够长吗？**
要。建议至少 32 字节的随机串，别用"123456"这种。密钥太弱等于没签名。

**Q：exp 用秒还是毫秒？**
用秒，和 `Date.now()/1000` 对齐。用毫秒会导致时间远在 1970 年附近，几乎立即过期。

**Q：RS256 验签需要私钥吗？**
不需要，公钥就够了。私钥只在签发时用，务必保管好；公钥本来就该公开分发。

**Q：为什么我的 token 验不过？**
先看 Header 的 `alg` 和验证时选的算法/密钥是否一致；再看 Payload 是否被改过（哪怕是空格）；HS 还要注意密钥一字不差。

**Q：工具里的密钥安全吗？**
完全在浏览器本地用 Web Crypto / WebAssembly 计算，不上传。但别在公共电脑上签完就把私钥留在输入框里。
